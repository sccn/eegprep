  • Implemented std_prepare_neighbors with a standalone distance-based channel-neighbor list and LIMO-compatible adjacency matrix. It does not call FieldTrip at runtime.
  • Implemented std_interp for STUDY channel-location unions using the existing EEGPrep channel interpolation backend. It preserves each dataset's existing channels when adding requested missing channels.
  • Added explicit std_dipplot and std_dipoleclusters limitation wrappers for STUDY-level source workflows that need Phase 3 DIPFIT/source contracts.

Tradeoffs And Boundaries

  • std_pac STUDY caches require a single freqphase value, matching the practical EEGLAB STUDY PAC cache shape. Use low-level pac directly for full amplitude-by-phase-frequency grids.
  • PAC bootstrap significance and EEGLAB's latphase histogram mode raise explicit NotImplementedError messages until they have a tested standalone backend.
  • Component-cluster PAC is not silently approximated. The cache writer raises until STUDY component/source contracts define how pairs should be matched across subjects and clusters.
  • LIMO model execution and result browsing remain external-only. The implemented design helper is intentionally limited to matrices and metadata that EEGPrep can own and test.

Verification Notes

  • Focused tests cover pac, pac_cont, std_pac, std_readpac, std_pacplot, std_limodesign, std_prepare_neighbors, std_interp, and source/LIMO limitation paths.
  • No new GUI dialog was introduced for Phase 4. Visual parity evidence remains on existing STUDY dialogs and plotting paths; the changed behavior is API/console/cache based.

Phase 5 Large-Dataset Storage Notes

This phase implements EEGPrep-owned storage behavior for issue #162 without adding runtime dependencies on the vendored EEGLAB tree or porting MATLAB @memmapdata/@mmo overloads one-for-one.

Design Decisions

  • Added MemmapData, a NumPy-compatible handle over EEGLAB-style .fdt sidecars. It preserves channel-major EEG shapes and uses the EEGLAB channel-fast float32 file layout for continuous and epoched data.
  • Added OffloadedData for option_storedisk. It records the saved .set path and shape metadata, but raises on sample access until the dataset is retrieved through eeg_retrieve or EEGPrepSession.retrieve.
  • Kept normal EEG dictionaries as the public contract. GUI and console synchronization flows through existing eeg_store, eeg_retrieve, and EEGPrepSession mutation points.
  • pop_saveset now accepts savemode="twofiles" and honors EEG_OPTIONS["option_savetwofiles"]. pop_loadset honors EEG_OPTIONS["option_memmapdata"] for sidecar-backed data.

Tradeoffs And Limitations

  • Unsaved resident datasets are not evicted under option_storedisk. This intentionally fails with a clear save-first error instead of pretending data was unloaded.
  • Single-file .set data still loads into memory; memory mapping is only honest for datasets with a separate .fdt sidecar.
  • EEGLAB pop_loadset channel-only and loadmode="info" paths are explicit non-implemented paths in Phase 5. Full dataset loading, storedisk retrieval, save/load, STUDY resave, and GUI/console synchronization are covered.
  • Derived caches such as icaact are not given a separate lazy storage layer in this phase.

Verification Notes

  • Added synthetic tests for two-file save/load, memory-map first/last sample access, sidecar mutation, missing-sidecar errors, default single-file behavior, and a slow large-sidecar smoke.
  • Added storedisk tests for offloading saved non-current datasets, rehydrating through eeg_retrieve, refusing unsaved eviction, pop_newset new-dataset behavior, STUDY resave, and mixed session/console synchronization.
  • Updated the final parity matrix rows for @memmapdata and @mmo to point at the Python-native storage backend and tests.

Issue #175 CLI Transform Command Notes

Design Decisions

  • Implemented the core transform slice in src/eegprep/cli/commands/transforms.py with argparse registration so the shared dispatcher can mount resample, rereference, filter, clean, epoch, and ica without importing GUI entry points.

Issue #175 Agent-Friendly CLI Closeout Notes

Design Decisions

  • Added the installed eegprep command as the headless agent/batch interface while leaving eegprep-gui and eegprep-console unchanged for human interactive use.
  • Organized commands by research workflow: discovery, inspect, validate, transforms, pipeline, batch, QC, report, BIDS, and EEGLAB migration helpers.
  • Bundled a version-matched eegprep-cli skill under resources/skills and exposed it through eegprep skills get eegprep-cli, so agents can load usage rules without scraping Sphinx docs.
  • Promoted PyYAML to a runtime dependency because config-driven pipelines are a core CLI feature, not only a development tool.

Tradeoffs And Boundaries

  • The CLI calls existing EEGPrep pop_* and plugin functions; it does not duplicate preprocessing math. This keeps parity behavior aligned with GUI and console workflows.
  • EEGLAB script conversion is intentionally best-effort. Unsupported MATLAB commands are reported with stable codes rather than silently guessed.
  • The CLI is headless and does not import GUI/IPython modules. Mixed GUI-plus-console workflows remain owned by eegprep-console.

Async GUI ICA Progress Notes

Design Decisions

  • Kept pop_runica itself synchronous for scripts, tests, CLI, and console calls. The background worker is owned by the Qt menu action layer because only the GUI needs to keep repainting while the computation runs.
  • Split pop_runica GUI option collection from ICA execution so the options dialog always opens on the main Qt thread and only the pure computation runs in the worker.
  • Session mutation remains on the main thread. The worker returns an updated EEG object and command string; EEGPrepSession is updated only from the success callback.

Tradeoffs

  • The progress dialog is indeterminate because runica progress is iteration/log-message based rather than a reliable percentage. Cancellation is intentionally not exposed until the ICA backends support safe interruption.
  • The reusable long-task helper captures EEGPrep log messages for the dialog, while the console action boundary keeps command echo and progress output ordered for mixed GUI-plus-console workflows.
